## 1. 为什么做这件事

## 2. 三 job ↔ 九道门对应表

> **⑧ 是后加的**（W0-D / LUM-1402，见 §10），**⑨ 也是后加的**（W0-E / LUM-1413，见 §11）：
> 本表已含它们，⑧ 之前的行是本切片（W0-A）的原始交付内容。

CI **不重写任何门禁命令**：每条 `run:` 都只是 `bash scripts/gates.sh --only <gate>`，
命令的唯一实现在 `scripts/gates.sh`。所以"本地怎么跑"和"CI 怎么跑"是逐字同一批命令，
不存在两处漂移（这是 gates.sh 存在的主要理由，不是省几个字符）。

| 门 | `--only <gate>` | 命令（`scripts/gates.sh` 内实现） | job | 需要 cargo | 需要 PG |
| --- | --- | --- | --- | :---: | :---: |
| ① | `fmt` | `cargo fmt --all --check` | `fast` | ✓ | — |
| ② | `build` | `cargo build --workspace --all-targets --locked` | `fast` | ✓ | — |
| ③ | `clippy` | `cargo clippy --workspace --all-targets -- -D warnings` | `fast` | ✓ | — |
| ④ | `clippy-test-util` | `cargo clippy -p mc-http --all-targets --features mc-http/test-util -- -D warnings` | `fast` | ✓ | — |
| ⑤ | `test` | `cargo test --workspace`（**剥掉 DB 变量**） | `fast` | ✓ | — |
| ⑥ | `db` | `cargo run -p mc-migrate -- run --dir migrations` → `cargo test -p mc-repos -p mc-http --features mc-http/test-util -- --ignored` | `db` | ✓ | ✓ |
| ⑦ | `route-parity` | `python3 scripts/route_parity.py --quiet` | `contract` | — | — |
| ⑧ | `schema-drift` | `python3 scripts/schema_drift.py --quiet`（判据=退出码；红了补打完整报告） | `db` | — | ✓ |
| ⑨ | `conformance` | `env -u MULTICA_TEST_DATABASE_URL -u MULTICA_DATABASE_URL cargo run -q -p mc-conformance -- --no-db --check crates/mc-conformance/report.json` | `contract` | ✓ | — |

job 侧要点（`ci.yml`）：

| job | runner 前置 | 说明 |
| --- | --- | --- |
| `fast` | `actions/checkout@v4` → `dtolnay/rust-toolchain@stable`（显式 `components: rustfmt, clippy`）→ `Swatinem/rust-cache@v2` | ①–⑤ 各占一个 step，Actions UI 上直接看到红色的是哪道门 |
| `db` | 同上 + `services.postgres`（`postgres:16`，`--health-cmd "pg_isready -U multica -d multica"`，`--health-retries 20`） | job 级 `MULTICA_TEST_DATABASE_URL`；⑥ 在 gates.sh 内部**先迁移再跑 e2e**；⑧ 在 ⑥ 之后，前置一个"确保 `psql`/`python3`"步（⑧ 建/删自己的 scratch 库，不读目标库的表） |
| `contract` | `actions/checkout@v4` → `dtolnay/rust-toolchain@stable` → `Swatinem/rust-cache@v2` → `actions/setup-python@v5`（3.12）；`timeout-minutes: 30` | **离线、不连库**（也不 clone 上游）：⑦ 只读 `docs/fixtures/upstream-routes.tsv` 与 `docs/fixtures/route-parity-baseline.json`（纯 Python）；⑨ 要 Rust 工具链跑一次 `cargo run -p mc-conformance`，把 58 条 golden fixture 打在本仓真实 router 上回放、并与 `crates/mc-conformance/report.json`（stateless 层快照）逐字节比对，漂移即红 |

触发与并发：`push` + `pull_request`（`branches: [main, feat/multica-rs-initial]`）+ `workflow_dispatch`；
`concurrency.group = ci-<workflow>-<ref>` 且 `cancel-in-progress: true`（同分支 push 风暴不排队）。

## 3. 本地复现

```bash
# 一键：①–⑤ + ⑦ + ⑨（不需要数据库）
bash scripts/gates.sh

# 含真库 ⑥ 与 ⑧（库必须已存在；⑥ 的 schema 由本脚本自己建，⑧ 自己建/删 scratch 库）
bash scripts/gates.sh --with-db --db-url 'postgres://multica:multica@127.0.0.1:5432/multica_test'
MULTICA_TEST_DATABASE_URL='postgres://…' bash scripts/gates.sh --with-db

# 单门（CI 就是这么调的）
bash scripts/gates.sh --only fmt
bash scripts/gates.sh --only db
bash scripts/gates.sh --only schema-drift
bash scripts/gates.sh --only conformance
bash scripts/gates.sh --list        # 列出 9 个闸门名
```

`scripts/gates.sh` 的行为契约：

* `set -u` + `set -o pipefail`；**不**用 `set -e` —— 默认是**收集式**（不 fail-fast），
  一道门红了继续跑完，最后给完整汇总表，便于一次看清"红了几道"。
* 每道门打印一行 `GATE_<NAME>_EXIT=<code>`（⑥ 另打 `GATE_DB_MIGRATE_EXIT` / `GATE_DB_E2E_EXIT`，
  `GATE_DB_EXIT` 是两者的合取）。末尾打印汇总表。
* 退出码：`0` = 选中的门全绿；`1` = 至少一道门非 0；`2` = 用法/前置条件错误
  （例如选了 ⑥ **或 ⑧** 却没给库 URL —— **绝不静默跳过**，这正是 `plan1` §6.4 第 4 条要的"不允许 skip"）。
* 脚本内部 `export PATH="$HOME/.cargo/bin:$PATH"`：本机 `/usr/bin/cargo` 是 1.75，解析不了本仓
  manifest（依赖里有 edition2024），不能靠调用者的 PATH。

## 6. 「Actions 是否实跑过」——诚实说明

**本切片交付的是 workflow 文件 + 一次已验证的本地七道门全绿，不是一次绿色的 Actions 跑。**
但"Actions 能不能认这个文件"已经实测过了：

* **Actions 在本仓是启用的，且已接受并调度了本 workflow**（实测，本切片 push 后）：
  `GET /repos/louloulin/paperclip-rs/actions/workflows` → `name: CI`、`path: .github/workflows/ci.yml`、
  `state: active`；`GET /actions/runs?head_sha=<本切片 head>` → `total_count: 1`，
  run `35736457657`，`event: pull_request`。
  这证明 YAML 通过了解析与 schema 校验（语法错的文件不会注册成 active、也不会被调度），
  也证明**不需要人工在仓库设置里做任何事**。
* **但该 run 的结论本切片不等**：切片明确要求不 `gh run watch` / 不 sleep 轮询，
  验收依据是 §5 的本地 exit code + §4 的期望数字，不是 Actions 的绿勾。见到的状态是 `queued`。
* 若首次 Actions 跑红了：**先看是不是工具链/资源差异**（见下一段），再看是不是 §7 的坑被"顺手优化"掉。
  本机在**严格带 `ci.yml` 同款 env** 下的冷启动是 7/7 绿（§4），所以红的位置本身就是信息。
* **已知差异**：CI 跑在 `ubuntu-latest` + 最新 stable，本机是 stable 1.98.1。
  两者若在不同小版本上对 fmt/clippy 有差异（真发生过：fmt 风格随版本微调），**以 CI 为准**。
  在 CI 变成强制门禁之前，本机 `bash scripts/gates.sh` 是本地唯一的真相来源。
* **本切片不配 branch protection、不做 "CI 必须绿才能 merge" 的强制**（那是仓库设置，超出切片范围，
  见 §9）。所以 CI 现在是「**信号**」，还不是「**闸门**」。

## 7. 例外与坑（都是本仓实测出来的，别"顺手优化"掉）

1. **⑤ 绝不能带 `MULTICA_TEST_DATABASE_URL`**。`crates/mc-http/Cargo.toml` 把根 `tests/smoke.rs`
   声明成名为 `smoke` 的集成 test target（虚拟 workspace 根没有 `[package]`，不声明就没人编译它）；
   该 target 里的 `workspace_member_http_e2e` 一拿到库就对**同一个库重跑迁移** →
   `relation "user" already exists`。所以 gates.sh 在 ⑤ 上用 **`env -u MULTICA_TEST_DATABASE_URL -u MULTICA_DATABASE_URL`**
   显式剥掉这两个变量 —— 即使调用者（或 CI job 的 `env:`）已经 export 过它，⑤ 也是安全的。
   *实测*：`MULTICA_TEST_DATABASE_URL=<真库> bash scripts/gates.sh --only test` → exit 0。
2. **③ 与 ④ 不可合并**。只有 `-p mc-http --features mc-http/test-util` 这一遍会检查
   `crates/mc-http/tests/*`（comments / contract_gaps / inbox / invitations / issues / pats / share_links）
   的 DB e2e 代码；workspace 那一遍**不覆盖**它们（feature 未开）。少了 ④，这 7 个文件的 warning 会漏网。
3. **⑥ 必须先建表**。`crates/mc-repos/src/**/db_tests` 与 `crates/mc-http/tests/*` 直接
   `INSERT INTO workspace`，**自己不做迁移** ⇒ `db` job 必须先 `mc-migrate run --dir migrations`。
   gates.sh 把这个前置放进了 `db` 门内部（而不是让 YAML 里再写一条命令），这样 `--only db`
   永远是"自足的"，挪到别处也不会漏。
4. **⑥ 的 DB 测试不清行**（`user` / `workspace` / `issue` 会残留）。带残留重跑仍绿，所以本机反复跑
   `--only db` 是安全的；CI 每次都是全新 service 容器，不涉及清理。（别在别人正跑 ⑥ 的时候去删行。）
5. **`--only` 与 `--with-db` 互斥**。`--with-db` 是"默认集合 + ⑥"；要精确指定就用 `--only`，
   两个一起给会 exit 2 —— 语义重叠时宁可报错，不要猜。
6. **⑨ 必须显式 `--no-db`（并剥掉库变量）**。`crates/mc-conformance/src/main.rs` 的 `--db-url` 声明了
   `env = "MULTICA_TEST_DATABASE_URL"`：谁 export 过这个变量（跑 ⑥/⑧ 的人都会），回放器就会追加 database 层，
   再把「两层取强者」的**合并报告**拿去和 `report.json`（stateless 层快照）比 → **门会因环境而红**。
   与 ⑤ 同一个套路：gates.sh 用 `env -u MULTICA_TEST_DATABASE_URL -u MULTICA_DATABASE_URL` 剥变量，
   同时显式给 `--no-db`（两道保险，任一生效都不会追库）。实测见 §11.2 的 RUN 3。

## 8. 未做 / 明确不做的（避免误以为"CI 已完备"）

| 项 | 状态 | 原因 |
| --- | --- | --- |
| `.github/ci-paths.json` 路径过滤 | **不做** | 收益（省几分钟）远小于风险（改 `crates/**` 却跳过 build）。`plan1` §6.4 要的是"必须全绿"，不是"尽量少跑"。宁缺毋滥。 |
| branch protection / 强制合并门禁 | **不做** | 仓库设置，超出本切片；见 §6 |
| `README` CI 徽章 | **不做** | 可选；徽章要有**完成过**的 run 才有意义（现在只有刚调度的 queued run），否则显示 "no status" 反而误导。且徽章是装饰不是门禁。 |
| `cargo nextest` / `cargo deny` | **未落地** | 本仓无 nextest 配置、无 `deny.toml` —— 都是独立切片的前置，塞进 `ci.yml` 只会让 CI 红着躺尸（`plan1` §6.3 的 drift 对账属 **W0③**） |
| `[workspace.lints]` 在成员 crate 推广（`lints.workspace = true`） | **不做** | 那是 **W0①** 的活（要动 17 个成员 `Cargo.toml`，与所有并发切片冲突） |
| 缓存/并行优化、矩阵构建 | 不做 | 冷启动 225s，还没到需要优化的量级 |

### 11.1 为什么 ⑨ 要 `--no-db` + `env -u`（不是多余的保险）

`report.json` 固定是 **stateless 层**快照（`docs/27` §7 第 3 条），而 `--db-url` 绑定了
`MULTICA_TEST_DATABASE_URL`。若 ⑨ 在这两个变量存在时运行，回放器会追 database 层、把**合并报告**
拿去比 stateless 快照，`--check` 必然报漂移 —— 那是**环境差异冒充契约漂移**，比红灯本身更坏。
`§11.2` 的 RUN 3 就是这个探针。

### 11.4 已登记的非等价项会不会污染默认集合

不会。⑨ 比的是「同一层次的快照」，不是「零 mismatch」：`pass 4 / mismatch 1 / unmounted 5 /
placeholder 1 / unevaluable 47` 都是 `report.json` **里已经写着的**数字，门只问「现在重跑还是不是这样」。
`/auth/google` 那条**回放器限制**（stateless 层固定 mismatch）不需要放宽口径。
`LUM-1410`（3 条 `POST /api/issues` 应 400 实测 201，属 database 层）已修好：⑨ 快照**未变**，
因为那 3 条在 stateless 层本就是 `unevaluable`（需 `member` 身份的真库层），修好后 diff 到的只有
database 层（`pass 40 → 43`，`docs/27` §5.1）。这恰好证实了“两层分开计数”的设计：快照门只锁 ci 口径，
不受真库层进展干扰；反过来说，如果哪天修的是 stateless 层能判定的 fixture，`report.json` 就**必须**
跟着 `--write` 刷新（`docs/27` §9 第 1 条的强制对账）。
