## 1. 为什么做这件事

`plan1.md` §7 的风险登记册里，**R2「无 CI → 质量债累积」的"概率"一栏写的是「已发生」**：
本仓历史上 M2-C 在 `cargo fmt` 不干净的树上合入主干，欠账 54 处，最后靠一个无关切片顺手清理。
根因不是"忘了跑 fmt"，而是**没有任何机器在合入前强制跑它** —— 门禁只存在于文档里。

顺带纠正一处文档漂移：本仓 `.github/` 在 `9b70556` 上**确实不存在**（不是"配了但没生效"）。
plan1 §6.2 画的 YAML 是**建议稿**，其中 `cargo nextest` / `cargo deny` / `schema_drift.py` /
`mc-conformance` 都**还没有落地前提**（本仓无 nextest 配置、无 deny.toml、无 schema 快照、
无 conformance crate）。本切片只固化**今天真实可跑**的七道门，未落地项见 §9。

## 2. 三 job ↔ 七道门对应表

CI **不重写任何门禁命令**：每条 `run:` 都只是 `bash scripts/gates.sh --only <gate>`，
命令的唯一实现在 `scripts/gates.sh`。所以"本地怎么跑"和"CI 怎么跑"是逐字同一批命令，
不存在两处漂移（这是 gates.sh 存在的主要理由，不是省几个字符）。

| 门 | `--only <gate>` | 命令（`scripts/gates.sh` 内实现） | job | 需要 cargo | 需要 PG |
| --- | --- | --- | --- | :---: | :---: |
| ① | `fmt` | `cargo fmt --all --check` | `fast` | ✓ | — |
| ② | `build` | `cargo build --workspace --all-targets --locked` | `fast` | ✓ | — |
| ③ | `clippy` | `cargo clippy --workspace --all-targets -- -D warnings` | `fast` | ✓ | — |
| ④ | `clippy-test-util` | `cargo clippy -p mc-http --all-targets --features mc-http/test-util -- -D warnings` | `fast` | ✓ | — |
| ⑤ | `test` | `cargo test --workspace`（**剥掉 DB 变量**） | `fast` | ✓ | — |
| ⑥ | `db` | `cargo run -p mc-migrate -- run --dir migrations` → `cargo test -p mc-repos -p mc-http --features mc-http/test-util -- --ignored` | `db` | ✓ | ✓ |
| ⑦ | `route-parity` | `python3 scripts/route_parity.py --quiet` | `contract` | — | — |

job 侧要点（`ci.yml`）：

| job | runner 前置 | 说明 |
| --- | --- | --- |
| `fast` | `actions/checkout@v4` → `dtolnay/rust-toolchain@stable`（显式 `components: rustfmt, clippy`）→ `Swatinem/rust-cache@v2` | ①–⑤ 各占一个 step，Actions UI 上直接看到红色的是哪道门 |
| `db` | 同上 + `services.postgres`（`postgres:16`，`--health-cmd "pg_isready -U multica -d multica"`，`--health-retries 20`） | job 级 `MULTICA_TEST_DATABASE_URL`；⑥ 在 gates.sh 内部**先迁移再跑 e2e** |
| `contract` | `actions/checkout@v4` → `actions/setup-python@v5`（3.12） | **纯离线**：只读 `docs/fixtures/upstream-routes.tsv` 与 `docs/fixtures/route-parity-baseline.json`，不 clone 上游、不装 Rust、不连库 |

触发与并发：`push` + `pull_request`（`branches: [main, feat/multica-rs-initial]`）+ `workflow_dispatch`；
`concurrency.group = ci-<workflow>-<ref>` 且 `cancel-in-progress: true`（同分支 push 风暴不排队）。

## 3. 本地复现

```bash
# 一键：①–⑤ + ⑦（不需要数据库）
bash scripts/gates.sh

# 含真库 ⑥（库必须已存在；schema 由本脚本自己建）
bash scripts/gates.sh --with-db --db-url 'postgres://multica:multica@127.0.0.1:5432/multica_test'
MULTICA_TEST_DATABASE_URL='postgres://…' bash scripts/gates.sh --with-db

# 单门（CI 就是这么调的）
bash scripts/gates.sh --only fmt
bash scripts/gates.sh --only db
bash scripts/gates.sh --list        # 列出 7 个闸门名
```

`scripts/gates.sh` 的行为契约：

* `set -u` + `set -o pipefail`；**不**用 `set -e` —— 默认是**收集式**（不 fail-fast），
  一道门红了继续跑完，最后给完整汇总表，便于一次看清"红了几道"。
* 每道门打印一行 `GATE_<NAME>_EXIT=<code>`（⑥ 另打 `GATE_DB_MIGRATE_EXIT` / `GATE_DB_E2E_EXIT`，
  `GATE_DB_EXIT` 是两者的合取）。末尾打印汇总表。
* 退出码：`0` = 选中的门全绿；`1` = 至少一道门非 0；`2` = 用法/前置条件错误
  （例如选了 ⑥ 却没给库 URL —— **绝不静默跳过**，这正是 `plan1` §6.4 第 4 条要的"不允许 skip"）。
* 脚本内部 `export PATH="$HOME/.cargo/bin:$PATH"`：本机 `/usr/bin/cargo` 是 1.75，解析不了本仓
  manifest（依赖里有 edition2024），不能靠调用者的 PATH。

## 6. 「Actions 是否实跑过」——诚实说明

**没有。本切片交付的是 workflow 文件，不是一次绿色的 Actions 跑。**

* 本机（agent runtime）不在 GitHub Actions 上，切片范围也**明确禁止** `gh run watch` / sleep 轮询
  等 Actions 结果，因此本切片的验收依据是**本地七道门的 exit code** + workflow 的结构化校验，两者都已在 §5 给出。
* `push` 之后 Actions 的行为（是否启用、私有仓额度、runner 是否限流）**取决于仓库设置，不在代码里**。
  若本仓库的 Actions 被关闭或额度受限，`ci.yml` 照常是有效文件，但不会自动跑；
  这种情况下"门禁"退化回"人手跑 `bash scripts/gates.sh`"，与今天等价，只是少了强制力。
* 另一个**已知差异**：CI 跑在 `ubuntu-latest` + 最新 stable，本机是 stable 1.98.1。
  两者若在不同小版本上对 fmt/clippy 有差异（真发生过：fmt 风格随版本微调），以 CI 为准。
  在 CI 变成强制门禁之前，本机 `bash scripts/gates.sh` 仍是本地唯一的真相来源。
* **本切片不配 branch protection、不做 "CI 必须绿才能 merge" 的强制**（那是仓库设置，超出切片范围，
  见 §9）。所以 CI 现在是「**信号**」，还不是「**闸门**」。

## 7. 例外与坑（都是本仓实测出来的，别"顺手优化"掉）

1. **⑤ 绝不能带 `MULTICA_TEST_DATABASE_URL`**。`crates/mc-http/Cargo.toml` 把根 `tests/smoke.rs`
   声明成名为 `smoke` 的集成 test target（虚拟 workspace 根没有 `[package]`，不声明就没人编译它）；
   该 target 里的 `workspace_member_http_e2e` 一拿到库就对**同一个库重跑迁移** →
   `relation "user" already exists`。所以 gates.sh 在 ⑤ 上用 **`env -u MULTICA_TEST_DATABASE_URL -u MULTICA_DATABASE_URL`**
   显式剥掉这两个变量 —— 即使调用者（或 CI job 的 `env:`）已经 export 过它，⑤ 也是安全的。
   *实测*：`MULTICA_TEST_DATABASE_URL=<真库> bash scripts/gates.sh --only test` → exit 0。
2. **③ 与 ④ 不可合并**。只有 `-p mc-http --features mc-http/test-util` 这一遍会检查
   `crates/mc-http/tests/*`（comments / contract_gaps / inbox / invitations / issues / pats / share_links）
   的 DB e2e 代码；workspace 那一遍**不覆盖**它们（feature 未开）。少了 ④，这 7 个文件的 warning 会漏网。
3. **⑥ 必须先建表**。`crates/mc-repos/src/**/db_tests` 与 `crates/mc-http/tests/*` 直接
   `INSERT INTO workspace`，**自己不做迁移** ⇒ `db` job 必须先 `mc-migrate run --dir migrations`。
   gates.sh 把这个前置放进了 `db` 门内部（而不是让 YAML 里再写一条命令），这样 `--only db`
   永远是"自足的"，挪到别处也不会漏。
4. **⑥ 的 DB 测试不清行**（`user` / `workspace` / `issue` 会残留）。带残留重跑仍绿，所以本机反复跑
   `--only db` 是安全的；CI 每次都是全新 service 容器，不涉及清理。（别在别人正跑 ⑥ 的时候去删行。）
5. **`--only` 与 `--with-db` 互斥**。`--with-db` 是"默认集合 + ⑥"；要精确指定就用 `--only`，
   两个一起给会 exit 2 —— 语义重叠时宁可报错，不要猜。

## 8. 未做 / 明确不做的（避免误以为"CI 已完备"）

| 项 | 状态 | 原因 |
| --- | --- | --- |
| `.github/ci-paths.json` 路径过滤 | **不做** | 收益（省几分钟）远小于风险（改 `crates/**` 却跳过 build）。`plan1` §6.4 要的是"必须全绿"，不是"尽量少跑"。宁缺毋滥。 |
| branch protection / 强制合并门禁 | **不做** | 仓库设置，超出本切片；见 §6 |
| `README` CI 徽章 | **不做** | 可选；且徽章在 Actions 尚未实跑前会显示 "no status"，反而误导 |
| `cargo nextest` / `cargo deny` / `schema_drift.py` / `mc-conformance` | **未落地** | 本仓无 nextest 配置、无 `deny.toml`、无上游 schema 快照、无 conformance crate —— 都是独立切片的前置，塞进 `ci.yml` 只会让 CI 红着躺尸（`plan1` §6.3 的 drift 对账属 **W0③**） |
| `[workspace.lints]` 在成员 crate 推广（`lints.workspace = true`） | **不做** | 那是 **W0①** 的活（要动 17 个成员 `Cargo.toml`，与所有并发切片冲突） |
| 缓存/并行优化、矩阵构建 | 不做 | 冷启动 225s，还没到需要优化的量级 |
