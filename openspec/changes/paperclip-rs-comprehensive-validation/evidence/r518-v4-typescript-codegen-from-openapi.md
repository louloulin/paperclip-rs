### 2. `pc-openapi` 修复 (R518 副产物)

**问题**: `DecisionOption` 和 `DecisionEffect` 是 `Decision` schema 通过 `$ref` 引用的 companions，但**从未被 `register_core_dtos` 注册**，导致 `components.schemas` 里只有 33 个；TS 生成器没法 emit 它们 → tsc 报错 `Cannot find name 'DecisionOption'`。

**修复**:
```diff
 pub fn register_core_dtos(reg: &mut OpenApiRegistry) {
     reg.register_schema_value("Decision", decision_schema());
+    // R518: companion schemas referenced by Decision.options / DecisionOption.effects.
+    reg.register_schema_value("DecisionOption", decision_option_schema());
+    reg.register_schema_value("DecisionEffect", decision_effect_schema());
     reg.register_schema_value("Company", company_schema());
```

`CORE_DTO_NAMES` 33 → 35，所有历史 `assert_eq!(CORE_DTO_NAMES.len(), 33)` 更新到 35。

### 3. 实现的 JSON Schema → TypeScript 转换特性

| JSON Schema | TypeScript 输出 |
|---|---|
| `{"type": "string"}` | `string` |
| `{"type": "integer"}` / `{"type": "number"}` | `number` |
| `{"type": "boolean"}` | `boolean` |
| `{"type": "null"}` | `null` |
| `{"type": "array", "items": {...}}` | `T[]` |
| `{"type": ["string", "null"]}` (OAS 3.1 nullable) | `string \| null` |
| `{"type": "string", "nullable": true}` (OAS 3.0 compat) | `string \| null` |
| `{"$ref": "#/components/schemas/Foo"}` | `Foo` (PascalCase) |
| `{"enum": ["a", "b"]}` | `"a" \| "b"` (排序, dedup) |
| `{"oneOf": [...]}` / `{"anyOf": [...]}` | `A \| B \| C` |
| `{"allOf": [...]}` | `A & B` |
| `{"type": "object", "properties": {...}, "required": [...]}` | `interface` + `?` suffix on optional |
| `{"additionalProperties": T}` | `Record<string, T>` |
| `{"const": "value"}` | `"value"` |
| `true` / `false` schema | `unknown` / `never` |
| `{"type": "string", "format": "date-time"}` | `string` (no special handling) |
| property name `x-rate-limit` | `x_rate_limit` (auto-rename) |

**fallback**: 未识别的 shape → `unknown` (永不 panic)

### 4. 不实现（明确的"不"）

- 不生成 fetch client（UI 端已经在 `ui/src/api/*.ts` 手写）
- 不生成 Zod schemas（R518 范围外；下一步 R519 可加）
- 不解析 `patternProperties` / `not` / `if-then-else`（fallback 到 `unknown`）
- 不解析 `$defs`（fallback 到 `unknown`）
- 不修改 `ui/` 现有手写 API 文件（避免 breaking change；后续 R519 让 UI 主动迁移）

## 设计要点

### 1. 单一真相源 (Single Source of Truth)

`pc_typescript_gen` **不重新定义任何 schema**。它直接消费 `pc_openapi::register_core_dtos(&mut reg)` 输出的 `OpenApiSpec`，然后 emit TS。

收益:
- 加新 DTO: 改 `pc-openapi::dto_schemas` 一处，TS 自动更新
- 改字段: 改一处，前后端类型自动同步
- 不存在「TS 漏改」「TS 跟实际 API 不匹配」的 drift

### 2. 纯函数 + 确定性输出

`generate_typescript_types` 是纯函数（无 IO、无副作用），输出：
- 按 schema 名字典序排序 → `git diff` 友好
- 按 property 名字典序排序 → 同上
- 两次生成字节级一致（已测试）

### 3. 不破坏既有 types

不修改 `ui/src/api/*.ts`（用户已经在那里手写了 60+ 端点 client）。R518 输出落到 `crates/pc-typescript-gen/generated/api-types.ts` 作为**可消费快照**，供后续 R519 让 UI 主动迁移到生成的类型。

### 4. 不依赖额外 npm 工具链

不调 `openapi-typescript` / `openapi-zod` / `swagger-codegen`。纯 Rust，编译时跑，输出 byte-stable TS。CI 里只需 `cargo test` + `tsc --noEmit` 即可验证。

### 5. Fallback 安全

未识别的 JSON Schema shape → emit `unknown`（永不 panic）。这意味着即使上游加了 `not` / `patternProperties` 等新特性，TS 至少能编译，UI 端拿到 `unknown` 后 IDE 会高亮提示「类型不完整」，强制开发者补生成器。
